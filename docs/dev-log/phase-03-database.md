# Phase 3: Database

- **Dates:** 2026-11-07
- **Status:** Done
- **Plan reference:** Implementation blueprint §2 (database stack), §4.6 (ledger), §5 (tables,
  lifecycle), §9.2 (invariants), §10.4 (integration tests), §11 Phase 3

## Goal

A migratable, seeded database: every MVP table with its CHECKs and indexes, the ledger view, the
deferred sum trigger (fixed per the plan corrections), role grants, a seed with currencies and the
Goa group, a `withTx` helper and an integration-test harness. Gate: integration tests showing the
trigger rejects bad sums at commit, the view excludes deleted transactions, and seeded nets match
core.

### Migrations (`packages/db/migrations/`)

| Migration         | Contents                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**The ledger trigger, corrected.** The plan's single function read `NEW.transaction_id` on
`transactions` rows (an error in PL/pgSQL) and didn't fire on DELETE. Now:

- `assert_transaction_balanced(tid)` checks Σ payers = Σ shares = amount (I1–I3). For settlements it
  also checks exactly one payer and one share, for different people (I9).
- `transactions` rows check their own `id`; payer and share rows check their transaction's ID.
  On an UPDATE, a row that moves to another transaction is checked against both the old and the new
  one.
- Triggers fire on INSERT, UPDATE and DELETE, and are deferred to COMMIT. An edit can therefore
  delete every row, change the amount and insert new rows before anything is checked.
- Violations raise `check_violation` with constraint `transaction_sums` or `settlement_shape`.

### Code (`packages/db/src/`)

- `client.ts`: `createDb(pool)`, the `Db` and `Tx` types, and `withTx(db, fn)`.
  `isLedgerInvariantError(err)` recognizes the trigger's errors through drizzle's error wrapping;
  `findPgError` is exported too.
- `migrate.ts`: `runMigrations(url)` applies migrations, then upserts the reference data.
- `reference.ts`: `CURRENCIES` (34 ISO 4217 currencies) and `applyReferenceData`.
- `seed/index.ts`: `seedDemo(db)` builds the Goa trip:
  - two demo accounts (Asha and Bilal, with `auth_user` rows) and two placeholders (Chitra and Dev)
  - the hotel, dinner, fuel and settlement transactions
  - the dinner correction, done through the real edit path: rows replaced, version 2, before/after
    activity snapshots
  - nine activity entries

  Every share is computed by core and the settlement fields are mapped by contracts. It's
  idempotent.

- `scripts/migrate.ts` and `scripts/seed.ts` are the CLI entry points. The seed refuses to run
  with `NODE_ENV=production`.
- `testing/`:
  - `setupTemplateDatabase()` (Vitest globalSetup) migrates `fairshare_test_template` once per run.
  - `createTestDatabase()` clones a fresh database for each test file, in milliseconds.
  - factories: `insertUser`, `insertGroup`, `insertTransaction`.

  All of it is exported as `@fairshare/db/testing` for the API's integration tests later.

### Repository wiring

- **Root scripts:** `pnpm db:migrate`, `pnpm db:seed`.
- **db package scripts:** `generate` (drizzle-kit) and `generate:auth` (Better Auth CLI, then
  Prettier).
- **CI:** `TEST_DATABASE_URL` is set, and a new step regenerates migrations and fails if anything

- **Turbo:** passes `TEST_DATABASE_URL` through to test tasks.
- **`.env.example`:** gains `TEST_DATABASE_URL`.

- **ESLint:** the db boundary now allows `core` and `contracts` only in `src/seed/**` and tests.

## Problems found and fixed

- **My own `groups_name` fix still had the NULL hole.** The first version, `(group AND length(name)
BETWEEN 1 AND 60)`, evaluates to NULL for a NULL name and passes. The constraint test caught it,
  and `name IS NOT NULL` was added. The plan's original has the same flaw.
- **drizzle's default `DESC NULLS LAST`** would have stopped the transaction feed and activity feed
  from using their indexes. Caught by reading the generated SQL; fixed before the first apply.
- **IDR decimals disagreed with Intl.** Caught by the new test comparing every currency with
  `Intl.NumberFormat`.
- **Test bugs:**
  - A `test.each` table referenced a user ID before `beforeAll` had assigned it.
  - A sequence query also counted drizzle's own migration sequence.
  - A hand-written `simplify` expectation had the transfers in the wrong order.
  - A test table needed an explicit row type, because TypeScript widened its string literals.
- **Lint:** the Vitest global-setup file sat outside the tsconfig, so it moved into `src/testing/`.
  A `sql.raw` in a CHECK became a literal, since the plan bans `sql.raw` outside migrations.
- **Bug-injection runner:** one injected bug broke setup instead of a test, and the runner counted
  that as "0 failures". The runner now reports runs that error before any test executes, and that
  bug was replaced with a meaningful one.

## Verification

- **97 integration tests** in `packages/db` (5 files), against real Postgres 17.
  - **Ledger (21):**
    - Balanced rows written in any order commit.
    - These are rejected at COMMIT with `transaction_sums`, and everything rolls back, including an
      activity row written in the same transaction: unequal shares or payers, no rows at all, an
      amount change without new rows, deleting or changing one share, and moving a share to
      another transaction.
    - The full edit path commits.
    - Settlements with two payers, two recipients, or the same person on both sides are rejected
      with `settlement_shape`.
    - The view gives paid − share, treats a settlement correctly, excludes deleted transactions and
      restores them exactly, keeps currencies apart, and every currency nets to 0.
    - EXPLAIN shows the feed query uses `tx_group_feed` without a sort, and search uses `tx_search`.
  - **Constraints (54):** every CHECK, unique index and key foreign key, each asserted by its exact
    constraint name. Also: citext email matching, one active owner per group, and the cap accepted
    exactly.
  - **Access (9):**
    - Owners can't UPDATE, DELETE or TRUNCATE activity.
    - Under `SET ROLE fairshare_app`: activity inserts work, updates fail, transactions can't be
      deleted, and currencies can't be changed.
    - `fairshare_readonly` can't write.
    - The exact privilege matrix holds for all 16 tables and views, plus sequence usage.
  - **Seed (6):**
    - Nets are **A +₹800, B +₹200, C −₹250, D −₹750**, the plan's numbers after the dinner
      correction.
    - They equal core's `netsFromTransactions` on the stored rows, and every stored transaction
      passes `assertTransactionInvariants`.
    - The edit is stored as version 2.
    - The nine activity entries hold snapshots that parse as `TransactionSnapshot`, and
      `diffSnapshots` reports the amount change.
    - A second run changes nothing.
  - **Migrations (7):**
    - All tables, the view, both extensions and all five triggers exist, with deferral flags.
    - Re-running migrations is a no-op.
    - The currencies load once, agree with Intl, and are corrected by the next run if changed.
- **Bug-injection check: 10 of 10 caught.** Each bug was applied to the real migration SQL or
  source:
  - share sums unchecked (3 tests failed)
  - share DELETE not checked (1)
  - self-settlement allowed (1)
  - view counting deleted payers (2)
  - payer trigger not deferred (17)
  - app granted DELETE on transactions (2)
  - append-only trigger on the wrong table (1)
  - app granted UPDATE on activity (1)
  - the plan's NULL-name CHECK (1)
  - IDR back to 2 decimals (1)

  The originals were restored; 97/97 pass and drizzle-kit reports no schema changes.

- **Real workflow:** on the dev database, `pnpm db:migrate` and `pnpm db:seed` both work, and
  running each a second run reports nothing to do.
- **Whole repo on Node 24.22.2:** format check, lint, typecheck, tests and build all pass. That's
  653 tests in total: core 247, contracts 275, api-client 25, api 9, db 97.

## Notes for later phases

- **Phase 4:**
  - Map `isLedgerInvariantError` to a 500 INTERNAL response, plus an alert.
  - Deploying needs a migration entry point that runs without `tsx` (for example a tsup bundle of
    `scripts/migrate.ts` with `migrations/` copied into the image).
  - Use two connection strings: the owner for migrations, and a login role in `fairshare_app` for
    the API.
  - Have the API use `createDb` from `@fairshare/db`.
- **Phase 5:**
  - The real Better Auth config must use the same model names and plugins as
    `auth-schema.config.ts`.
  - Its tables use `timestamp without time zone`, so keep the database session time zone at UTC.
    That's the default on Docker Postgres and Neon.
  - The seeded Asha and Bilal accounts can sign in by OTP through Mailpit.
- **Phase 6:** `fairshare_app` has no DELETE on `group_members`. The merge must abort when the
  claimer has any row in the group, including one where they left (already a plan correction),
  which also avoids a primary-key clash.
- **Phase 7:**
  - Keyset queries must `ORDER BY occurred_on DESC, id DESC` to use `tx_group_feed`.
  - Search must use the exact expression `(description || ' ' || coalesce(notes, ''))`.
  - `sum()` over bigint returns a numeric string, so cast it.
  - Store blank notes as NULL.
- **Performance (Phase 13 load test):** the checks are per-row triggers, so editing a 50-person
  expense runs the check about 100 times at commit. That's negligible at this scale. If profiling
  says otherwise, switch to statement-level triggers with transition tables.
